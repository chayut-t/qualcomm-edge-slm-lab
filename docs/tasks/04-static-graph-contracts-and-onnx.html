Task 04 — Static graph contracts and ONNX

Lab: notebooks/04_static_graphs_and_onnx.ipynb + src/edge_slm_lab/static_wrapper.py + src/edge_slm_lab/onnx_tools.py + tests/test_shape_contracts.py · Estimated time: 2.5–3 hours

1. Why this matters for Qualcomm work

In Task 03 you ran the decode loop in Python. Each step passed a DynamicCache object back into the model. That object is Python. An NPU cannot run Python.

A Snapdragon bundle is compiled ahead of time. The compiler must know, before any input exists:

  • every input and output tensor, by name;
  • each tensor's dtype;
  • each tensor's exact shape, as plain integers.

This full list is the graph's contract. With a fixed contract the compiler can plan memory, pick kernels, and fuse operations once, at compile time. That is where the NPU speed comes from. The price: the compiled graph accepts only the shapes it was frozen with.

ONNX is the standard file format for such frozen graphs. Qualcomm's export path goes through this kind of representation before it becomes a QNN context binary. In this task you make the freeze visible on a tiny model you can export in seconds.

  • The full interface of Qwen3-0.6B's decode step: 57 tensors in, 57 tensors out.

4. A simple mental model

Think of a compiled graph as a sealed machine with labeled sockets. Every socket has a name and a fixed plug size. Nothing else fits. Your Task 03 loop, translated to sockets, becomes two machines:

The cache is no longer a hidden Python object. It goes in as past_key_i / past_value_i tensors and comes out as present_key_i / present_value_i tensors, one token longer. The loop that Task 03 wrote in Python becomes: run decode graph, take its present_* outputs, feed them back as the next step's past_* inputs.

Key idea

A dynamic model answers "what shapes?" at run time. A static graph answers it at export time, once, forever. Everything a Snapdragon bundle fixes — context limit, cache layout, prompt lengths — is this same freeze, applied at compile time. New shape ⇒ new graph.

5. Exact technical details

The lab uses the tiny random Qwen3 from the Task 03 tests (2 layers, 4 query heads, 2 KV heads, head_dim 16, vocab 128). Same layer type and cache layout as Qwen3-0.6B, tiny numbers, so exports take seconds. The contract of the two exported graphs, at PROMPT_LEN = 8:

TensorPrefill graphDecode graph
input_ids (in)[1, 8] int64[1, 1] int64
past_key_i / past_value_i (in)— none[1, 2, 8, 16] float
logits (out)[1, 8, 128] float[1, 1, 128] float
present_key_i / present_value_i (out)[1, 2, 8, 16][1, 2, 9, 16]

Three facts about the ONNX file itself:

  • Weights are initializers. They live inside the file as constants, not as inputs. So the input list shows only what a caller must supply.
  • The opset pins the operator dictionary. We export with opset_version=17. Every node (MatMul, Softmax, Concat, …) means exactly what opset 17 defines.
  • Export is tracing. torch.onnx.export with dynamo=False runs the model once with an example input and records every tensor operation. Python control flow, the cache object, and all shape logic disappear. Only the recorded operations remain, with shapes frozen to the example.

Scaled up to the real model, from its config (28 layers, 8 KV heads, head_dim 128, vocab 151,936), the decode contract at cache length 24 is:

  • inputs: input_ids [1, 1] plus 28 × 2 = 56 cache tensors [1, 8, 24, 128] → 57 inputs;
  • outputs: logits [1, 1, 151936] plus 56 cache tensors [1, 8, 25, 128] → 57 outputs.
Watch for

Our decode graph is frozen at one cache length. Real bundles cannot ship one graph per length. They allocate the cache at the context limit and use an attention mask to hide unused slots. That is why a bundle has a hard context limit: the cache buffers were sized at compile time. Our lab skips the padding to keep the freeze itself visible.

6. One worked example — the decode wrapper, line by line

The whole trick of src/edge_slm_lab/static_wrapper.py is to move the cache across the Python/graph boundary:

class DecodeWrapper(nn.Module):
    def forward(self, input_ids, *past):
        cache = DynamicCache()
        for i in range(self.n_layers):
            cache.update(past[2 * i], past[2 * i + 1], i)
        out = self.model(input_ids=input_ids, past_key_values=cache, use_cache=True)
        return (out.logits, *_flat_kv(out.past_key_values, self.n_layers))
  • *past — the cache arrives as plain tensors: past_key_0, past_value_0, past_key_1, past_value_1. Plain tensors can be graph inputs. A cache object cannot.
  • cache.update(keys, values, i) — rebuilds the Hugging Face cache from those tensors, layer by layer. Inside the trace this is just tensor bookkeeping, so it records cleanly.
  • self.model(...) — the same call your Task 03 loop made. Nothing about the model changed. Only the interface around it did.
  • return (out.logits, *_flat_kv(...)) — flattens the grown cache back into plain tensors, so the graph can output it.

During export, tracing runs this once with example tensors of the chosen size and records the result. The recorded graph has no loop, no if, no cache class — check the operator counts in the notebook: mostly MatMul, Mul, Add, Softmax, Concat.

Optional extension — one graph, many steps (Part 6)

Parts 1–4 leave a fair question: if the cache length is frozen into the graph, how does a real bundle decode 100 tokens with one graph? Part 6 of the notebook answers it by building the real design in miniature. The rule: move everything that varies from shapes into values.

TensorShape (fixed forever)What varies per step
input_ids (in)[1, 1]the token id
position_ids (in)[1, 1]the RoPE position of the new token
attention_mask (in)[1, 1, 1, MAX_LEN + 1]which slots are visible (0.0) vs hidden (a huge negative number)
past_key_i / past_value_i (in)[1, 2, MAX_LEN, 16]the buffer contents; empty slots stay zero
new_key_i / new_value_i (out)[1, 2, 1, 16]the new token's K/V only

The graph never writes the cache. The host loop copies new_key_i into the next free slot of its padded buffer, advances filled by one, and updates the mask. A real runtime does this same bookkeeping around the compiled graph. The mask works by addition: scores of hidden slots get MASK_MIN added before softmax, so their attention weight becomes zero.

The check at the end is the payoff: 12 tokens through one frozen graph, token ids identical to Task 03's greedy_decode. And the context limit appears as a hard assert — slot MAX_LEN does not exist, so PROMPT_LEN + N_STEPS may not exceed MAX_LEN = 32. That limit was chosen at export time, exactly like a bundle's context limit is chosen at compile time.

12. Knowledge check (optional)

1. Why can't the compiled graph take Task 03's DynamicCache as an input?

It is a Python object with methods and state. A graph input must be a named tensor with a fixed dtype and shape. So the wrapper flattens the cache into past_key_i / past_value_i tensors.

2. The decode graph declares past_key_0 [1, 2, 8, 16] and present_key_0 [1, 2, 9, 16]. What sentence from Task 03 is this?

"The cache grows by exactly one token per decode step." Dimension 2 is the cache length: in at 8, out at 9.

3. Where are the model weights in the ONNX file?

They are initializers: constants stored inside the graph. They are not inputs, so the declared input list shows only what the caller must supply.

4. For Qwen3-0.6B, why does one decode step have 57 inputs?

1 for input_ids [1, 1], plus 2 cache tensors (key and value) × 28 layers = 56. Total 57. The KV cache is almost the whole interface.

5. A real bundle serves many cache lengths with one compiled graph. Our lab graph serves exactly one. What closes the gap?

The bundle allocates the cache at the context limit at compile time and masks the unused positions. Fixed buffers, moving fill level. That is also why the context limit cannot be raised at run time.

14. Page glossary and sources

  • ONNX — Open Neural Network Exchange: a file format for a frozen operator graph with named, typed, shaped inputs and outputs.
  • opset — the versioned dictionary of ONNX operators a graph is written against. This lab pins opset 17.
  • initializer — a constant tensor stored inside an ONNX graph, mainly the weights.
  • static shape — a tensor dimension fixed to one integer in the graph itself, decided at export or compile time.
  • tracing — exporting by running the model once with example inputs and recording every tensor operation.
  • ONNX Runtime — the engine (onnxruntime) that loads an ONNX file and executes it, enforcing its contract.
