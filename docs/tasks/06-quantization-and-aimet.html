Task 06 — Quantization and AIMET concepts

Lab: notebooks/06_quantization_fundamentals.ipynb · Model: Qwen/Qwen3-0.6B real weights, local float copy · Estimated time: 2.5–3 hours

1. Why this matters for Qualcomm work

The bundle you will fetch in Task 07 is W4A16: weights stored as 4-bit integers, activations as 16-bit integers. Quantization is the step that turns float numbers into those small integers. It is where the model gets small and fast — and where error enters.

In Task 05 you found the hooks: SPINQUANT_CONFIG, get_weight_optimization_data, get_calibration_data, and quantize.py calling llm_quantize. This task explains what those hooks do. You will also build the core operation — symmetric fake quantization — with your own hands, on real Qwen weights.

Fact vs teaching code: your lab quantizes weights only, with simple max-based scales. Qualcomm's real recipe adds rotations (SpinQuant), learned scales (AdaScale), and activation calibration (AIMET). Section 5.6 draws that line clearly.

4. A simple mental model

A float32 weight can take billions of distinct values. A 4-bit integer can take only 16. Quantization is a ruler with very few marks: every weight must snap to the nearest mark.

You store two things per group of weights: the integer for each weight, and one shared float called the scale — the distance between marks. Small integers plus one scale is much cheaper than a float per weight. That is the whole memory win.

The error is the snap distance. Two things control it:

  • Bit width: more bits, more marks, smaller snaps.
  • Scale quality: the scale is set by the biggest value in the group. One huge outlier stretches the ruler, so every normal weight lands between marks that are far apart.

Everything in Qualcomm's recipe attacks the second problem: grouping shrinks the region one scale must cover, SpinQuant spreads outliers out, AdaScale tunes the scales on data.

5. Exact technical details

5.1 The symmetric quantization formula

For a group of weights w and bit width b:

qmax = 2**(b - 1) - 1          # largest positive integer level
s    = max(|w|) / qmax          # scale: float distance between levels
q    = clamp(round(w / s), -qmax, qmax)   # stored integer
w_fq = q * s                    # dequantized (fake-quantized) value

Every symbol:

  • b — bit width. For W4A16 weights, b = 4, so qmax = 7 and levels run −7…7.
  • max(|w|) — the largest absolute value in the group. This one number sets the ruler for the whole group.
  • s — the scale. Stored as a float next to the integers.
  • q — the integer code that is actually stored, 4 bits each.
  • w_fq — the value the hardware effectively computes with. The error is w - w_fq, at most s / 2 per weight from rounding.

Symmetric means the levels are centered on zero, so no offset number is needed. Asymmetric schemes add an offset (zero point); AIMET encodings can store one, but your lab stays symmetric.

Fake quantization means: snap the values, then keep computing in float. The numbers behave like 4-bit numbers, but no integer kernel runs. AIMET's QuantizationSimModel (QuantSim) does exactly this at scale, so accuracy can be tested before any device compile.

5.2 What W4A16 means

W4A16 = weights stored as 4-bit integers, activations quantized to 16-bit integers. A16 is INT16, not FP16. The pinned tutorials/llm/onboarding.md draws the line itself: it describes w4a16 as "quantizing both weights and activations," and contrasts it with w4, which it defines as "quantized weights and floating-point activations." Each 16-bit activation tensor carries a calibrated scale from the encodings — that is why calibration exists at all. Float activations would need none.

Facts from the pinned code and tutorial:

  • SUPPORTED_PRECISIONS = [Precision.w4a16] — the only published precision for Qwen3-0.6B (qwen3_0_6b/model.py line 86).
  • Qualcomm's tutorial: 4-bit weights cut size, memory traffic, and latency; for edge they also quantize activations — this "makes the model more suitable for edge hardware and leads to better performance" (tutorials/llm/quantize_llama3.md).

Why quantize activations at all? Three reasons stack up:

  • The NPU's fast path is integer math. INT4-weight × INT16-activation matmul runs on the integer multiply-accumulate hardware. With float activations, every matmul would first convert the weights back to float — keeping the storage win but losing the compute win. (The tutorial quote above is the fact; which exact chip units run what is inference from Qualcomm's public material.)
  • Activations are memory traffic — and the KV cache is activations. From your Task 05 contract, each token moves (8, 1, 128, 4095) keys plus the same in values, times 28 layers, across the graph boundary. At 16 bits that traffic is half of float32. On a phone, bandwidth is often the real limit.
  • A compiled static graph needs fixed formats. The QNN context binary bakes in every tensor's scale, offset, and bit width. That is what the calibrated encodings provide — and why the mask uses −50 instead of −∞ (section 5.4): every activation must fit a range a fixed integer grid can cover.

Why 16 bits and not 8? Accuracy: "we primarily use 16-bit activations, leveraging 8-bit activations only where feasible" (quantize_llama3.md). Activation outliers are worse than weight outliers, and they cannot be fixed offline — so activations get 65,536 levels while weights get 16.

Rough size math: 596,049,920 parameters (your Task 02 count) × 4 bits ≈ 284 MiB, before scales and overhead. Float32 was ~2.2 GiB.

5.3 Grouping: who shares a scale

A linear layer weight is a 2-D tensor, for example model.layers.0.self_attn.q_proj.weight with shape (2048, 1024) — 2048 output rows, 1024 inputs. The grouping choices, from coarse to fine:

  • Per-tensor: one scale for all 2,097,152 weights. One outlier anywhere hurts everyone.
  • Per-channel: one scale per output row (2048 scales). An outlier only hurts its own row.
  • Per-group (also called per-block): split each row into blocks of, say, 128 or 32 inputs. An outlier only hurts its block of 128 or 32 neighbors.

The cost: more groups means more stored scales and more hardware bookkeeping. Your lab measures the benefit side directly.

5.4 Calibration and encodings (AIMET)

Weights are known ahead of time, so their ranges are easy. Activation values depend on the input, so their ranges must be measured. Calibration runs representative text through the fake-quantized model and records the observed ranges. In the pinned code this is one line: self.quant_sim.compute_encodings(...) (utils/quantization_aimet_onnx.py).

Be precise about what calibration is: measurement, not learning. One forward pass over the samples, no gradients, no iterations. It changes nothing about the weights. The step that optimizes on data is AdaScale (section 5.5) — the two are easy to confuse because both consume text, so section 5.6 puts them side by side.

The result is saved as encodings: the file model.encodings holding every scale and offset. A quantized checkpoint is exactly: ONNX graphs (for example model_ar128_cl4096.onnx), a shared weights file model.data, and model.encodings (tutorials/llm/quantize_llama3.md, "Checkpoints").

Facts about Qwen3-0.6B's calibration data (from Task 05's map):

  • Calibration uses InterleavedGeneratedWikitext: text the model generated itself from seed prompts in calibration_prompts.yaml, interleaved with WikiText train data.
  • Default sample count is small: --num-samples defaults to 20 (_shared/llm/quantize.py line 297).
  • Quantization runs on the AR-2048 graph — long sequences, GPU friendly (tutorials/llm/onboarding.md).

Connection to Task 05: the mask uses −50 instead of −∞ because "Mapping the real range (-∞, 0] to a quantized range is impractical." That design choice exists purely so calibration sees a small, coverable range.

5.5 SpinQuant and AdaScale, at concept level

Max-based scales have one enemy: outliers. LLM weights and activations have heavy tails — a few values are far larger than the rest. Two methods in the recipe fight this before calibration runs.

SpinQuant — rotate so outliers spread out. Multiply a weight matrix by an orthogonal matrix Q (a rotation, Q @ Q.T = I). Insert Q in one place and Q.T in the matching place, so the network computes the same function. Nothing about the math changes — but the numbers change. A rotation mixes every value with its neighbors, so one giant value becomes many medium values. max(|w|) drops, the scale drops, and every rounding error shrinks. Facts from the pinned code:

  • Qwen3-0.6B uses SPINQUANT_CONFIG = {"enable_r1": False, "enable_r2": True, "enable_r3": True} (qwen3_0_6b/model.py line 93).
  • R2 rotates inside attention, on the value path: the implementation matches v_proj nodes by name and co-rotates the paired output projection (utils/quantization_aimet_onnx.py, apply_spinquant_to_onnx). The rotation folds into the existing weights — no new ops at run time.
  • R3 is different: it "inserts plain-float Hadamard MatMuls" into the graph (same file) — small extra multiply ops that rotate activations on the fly, then the next weight matrix absorbs the inverse. A Hadamard matrix is a cheap fixed rotation of ±1 entries.
  • R1 (a whole-network rotation of the residual stream, absorbed into embeddings and output weights) is off for this model. Labeled inference: at 0.6B, the R1 gain likely did not justify it; the config records the choice, not the reason.
  • The rotations run in Phase 2 of quantize(), on the float ONNX graph, before the quantization simulator is built (_shared/llm/quantize.py lines 168–172).

Which layers get rotated? Only attention. With R2 and R3 attention-side and R1 off, the MLP matrices — gate_proj, up_proj, down_proj — receive no rotation in this model. The SpinQuant paper has an MLP pass (R4, a Hadamard before down_proj), but this repo's valid passes are only r1, r2, r3 (_shared/llm/quantize.py line 40). The MLP is still not "vanilla" quantized, though: AdaScale optimizes its weight scaling and calibration sets its activation encodings. Only the rotation step skips it. Your Part 6 demo rotates down_proj — so you will see how much a rotation could help exactly where Qualcomm chose not to apply one.

Method background (paper, not Qualcomm code): SpinQuant, arXiv 2405.16406.

AdaScale — learn the scaling instead of taking the max. The max-based scale in your lab is safe but wasteful: it spends grid range on one rare value and leaves most weights coarsely rounded. AdaScale replaces that rule with an optimization. AIMET's own documentation defines it: a post-training technique that "recovers accuracy lost during INT4 weight quantization without any fine-tuning" by "learning optimal per-weight scaling parameters through Blockwise Knowledge Distillation (BKD): the quantized output of each transformer block is optimized to match its FP32 equivalent until the two converge." So the target is not the per-weight snap distance — it is the block's actual output error on real data. Note the grain: per-weight, finer than the per-channel scales in your lab. It builds on FlexRound and takes learnable weight clipping from OmniQuant. Facts from the pinned code:

  • AdaScale runs on plain WikiText train data through get_weight_optimization_data (qwen3_0_6b/model.py lines 169–171) — a different dataset hook than calibration. That is why Task 05 found two data hooks.
  • It needs a CUDA GPU. CPU raises: This quantization technique requires a CUDA GPU (V100/A100). Please re-try with GPU machine. (_shared/llm/quantize.py lines 122–125). The code also warns it "can take hours to complete."
  • Qwen3 needs a model-specific hint: ada_scale_num_rmsnorm_per_blk = NUM_ATTN_HEADS + NUM_KEY_VALUE_HEADS + 1 = 25, because the split-head patch from Task 05 turned each block's few RMSNorms into 25 (qwen3_0_6b/model.py line 139).
  • AIMET applies it via AdaScale.apply_adascale(...) from aimet_onnx.experimental.adascale.

5.6 The full recipe, in execution order

From quantize() in _shared/llm/quantize.py, the published recipe SpinQuant R2 + R3 -> AdaScale -> calibration maps to:

PhaseWhat runsNeeds data?What it fixes
1. Exportexport_onnx: float model → ONNX No—
2. SpinQuantapply_pre_sim_transforms: R2 + R3 rotations on the float graph No — pure algebraSpreads outliers before anything is quantized
3. QuantSimBuild the fake-quantization simulator at the chosen precision (w4a16)No—
4. AdaScalequantize(use_ada_scale=True, ...) optimizes weight scalingYes — WikiText train Better scales than plain max
5. Calibrationcompute_encodings measures activation rangesYes — interleaved generated text + WikiTextActivation encodings for the A16 side

Output: a quantized checkpoint (model.encodings + ONNX + model.data). Task 07 hands that to AI Hub, which compiles it into the QNN context binary.

AdaScale vs calibration, side by side. Both consume text, so keep them apart:

AdaScaleCalibration
Changesweight scaling (per-weight) activation encodings (the A16 side)
Methodoptimization: match each quantized block's output to its FP32 output measurement: observe ranges, compute scale and offset
DataWikiText train, via get_weight_optimization_data interleaved generated text + WikiText, via get_calibration_data
CostCUDA GPU, iterations, hours one forward pass over ~20 samples
Orderfirstlast

The order matters: calibration measures activations flowing through the final weights. Rescale weights afterward and the measured ranges would be stale. The pinned quantize() method runs them in exactly this order (utils/quantization_aimet_onnx.py: AdaScale, then "Start QuantSim calibration"). One-line version: AdaScale learns how to store the weights. Calibration measures how big the activations get.

Key idea Your lab implements only the formula from 5.1, on weights only. Qualcomm's pipeline wraps that same formula with rotations (step 2), learned scales (step 4), and measured activation ranges (step 5). The teaching code is the skeleton; the recipe is the muscle around it.

6. One worked example, by hand

Quantize four weights at b = 4: w = [0.02, -0.01, 0.03, 1.50]. The last value is an outlier.

qmax = 2**(4-1) - 1 = 7
s    = max(|w|) / qmax = 1.50 / 7 = 0.2142857
q    = round(w / s)  = [round(0.093), round(-0.047), round(0.140), round(7.0)]
                     = [0, 0, 0, 7]
w_fq = q * s         = [0.0, 0.0, 0.0, 1.50]

The outlier survives perfectly. The three normal weights are erased — 100% error. Now drop the outlier into its own group:

group 1: [0.02, -0.01, 0.03]   s = 0.03 / 7 = 0.0042857
         q = [5, -2, 7]        w_fq = [0.0214, -0.0086, 0.0300]
group 2: [1.50]                exact

Same bits, tiny error. That is the whole argument for grouping, and the notebook's self-test checks these exact numbers.

11. Common mistakes and debugging clues

  • Thinking the lab is W4A16. It is W4-only: activations stay float. Real W4A16 also quantizes activations to 16-bit using calibrated encodings (section 5.4).
  • Thinking fake quantization saves memory. It does not — values are float again after the snap. It only predicts the accuracy of the real integer version.
  • transformers was already imported assertion. Restart the kernel and run the setup cell first, so the cache path points at T9 before any download logic runs.
  • Out-of-memory on load. The float32 model needs ~2.4 GB. Close other kernels (Tasks 02–04) first.
  • Error goes up with more bits. Impossible with this formula — if you see it, a group size probably does not divide 1024 or 3072 evenly; the function asserts on that.
  • Comparing across different weights. Relative error is only comparable on the same matrix. The plots never mix them on one line.

12. Knowledge check

  1. In W4A16, what is stored in 4 bits and what runs in 16 bits?
    AnswerWeights are stored as 4-bit integers (plus scales). Activations — the values flowing between layers — are quantized to 16-bit integers using calibrated ranges.
  2. One weight in a per-tensor group is 100× larger than the rest. What happens to the others?
    AnswerThe scale is set by that outlier: s = max(|w|)/qmax. The grid spacing becomes ~100× too coarse for normal weights, so they round to very few levels — many to exactly zero, like the worked example.
  3. Why does rotating a weight matrix by an orthogonal Q not change what the network computes?
    AnswerThe inverse rotation Q.T is inserted at the matching place (folded into the paired weight, or applied as a small extra op like R3's Hadamard MatMuls). Since Q @ Q.T = I, the composed function is identical — only the stored numbers differ.
  4. Calibration needs data but AdaScale also needs data. What is the difference in what each produces?
    AnswerAdaScale optimizes weight scaling using WikiText train data, before calibration. Calibration (compute_encodings) measures activation ranges on the interleaved generated + WikiText data and writes the final encodings.
  5. Why do the SpinQuant rotations run before the QuantSim is built?
    AnswerThey must transform the float graph: the rotations change the weight values that the simulator will then quantize, and R3 inserts float Hadamard MatMul ops that the simulator must wrap with quantizers. Rotating after would miss both (apply_pre_sim_transforms, Phase 2).

14. Page glossary and sources

Quantization
Mapping float values to a small set of integer levels plus a scale.
Scale
The float distance between integer levels; one per group.
Symmetric quantization
Levels centered on zero; no offset stored.
Fake quantization
Snap values to the grid but keep computing in float, to predict accuracy.
Group
The set of weights sharing one scale: whole tensor, one channel, or a block.
Outlier
A value far larger than its neighbors; it stretches the scale.
Calibration
Measuring activation ranges on sample data (compute_encodings).
Encodings
The saved scales and offsets (model.encodings).
SpinQuant
Orthogonal rotations (R1/R2/R3) that spread outliers before quantization. In this model: attention only.
AdaScale
Learns per-weight scaling through Blockwise Knowledge Distillation, on a GPU, before calibration.
W4A16
4-bit integer weights, 16-bit integer (INT16, not FP16) activations.
