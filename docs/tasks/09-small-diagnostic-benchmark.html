Task 09 — Small diagnostic benchmark

Lab: reusable command-line benchmark on your Mac, plus an import of your Task 08 device numbers · Estimated time: 2–3 hours; each benchmark run about 5–10 minutes

1. Why this matters for Qualcomm work

Task 08 gave you two speed numbers from the phone: TTFT about 20 ms and decode about 108 tokens/s. Those are two different measurements of two different phases. A single "tokens per second" number would hide that. This task builds a small benchmark that always measures the two phases separately, on eight realistic prompts, at three prompt lengths.

The core question: why must TTFT and decode throughput be measured separately? You will answer it with your own numbers. Prefill processes the whole prompt in one parallel pass. Decode produces one token per pass, in a serial loop. The two phases scale differently with prompt length, so one number cannot describe both.

Task 08 also left two open findings. First, the device decode was about three times faster than the ceiling we guessed from Task 07's profile. Second, context length 512 vs 4096 made no measurable difference on the phone. This benchmark gives you the local side of that picture, with a prompt-length sweep the phone run did not have.

2. What you will understand after this task

  • What TTFT, prefill tokens/s, and decode tokens/s measure, as formulas you computed yourself.
  • How TTFT scales with prompt length, and why decode speed mostly does not.
  • Why a warm-up run comes before the measured runs.
  • Why timing on Apple's GPU needs torch.mps.synchronize() — and what a benchmark measures without it.
  • Why numbers from unlike runtime paths must carry a warning, never sit in the same average.
  • Why a benchmark records null for a missing metric instead of estimating it.

3. Prerequisites

  • Task 03: the greedy decode loop with an explicit KV cache. The benchmark reuses that exact loop shape: prefill once, then one token per step.
  • Task 08: your device numbers in results/08_qdc_geniex.json and the pulled cell JSONs on T9 at artifacts/task08/pulled/results.
  • Task 08 finding to test: on the phone, prompt_tokens was always 128 because geniex-bench fills the prompt_ar128 graph. Locally there is no fixed prompt graph, so TTFT is free to change with prompt length.
  • The local float model from Task 02: Qwen/Qwen3-0.6B, already in your Hugging Face cache.

4. A simple mental model

Think of answering a letter. First you read the whole letter. That is prefill: one pass over all prompt tokens at once. Reading a longer letter takes longer, but you read all lines in one sitting. Then you write your reply one word at a time. That is decode: each new token needs a full pass through all 28 layers, and it cannot start before the previous token exists.

TTFT is how long the sender waits before your first word appears. Decode tokens/s is your writing speed after that. A long letter makes the wait longer but does not change your writing speed much. That is why the two metrics must stay separate.

5. Exact technical details

5.1 The three metrics

For one measured run with prompt length P tokens and G generated tokens:

  • ttft_ms = t_first_token - t_start. The clock starts when the prompt tensor is ready and stops when the first new token id exists on the CPU. This one forward pass has input shape [1, P].
  • prefill_tps = P / ttft_s. Prompt tokens processed per second during that pass. ttft_s is the same time in seconds. This is derived from two measured values, not estimated.
  • decode_tps = S / decode_s. S = G - 1 is the number of one-token decode steps (the first token came from prefill). decode_s is the measured wall time of the whole decode loop. Each step has input shape [1, 1] and grows the KV cache by one.
Key idea

Prefill cost grows with P. Decode cost per token is roughly constant, because each step always feeds one token. So TTFT and decode tokens/s answer two different questions: "how long until something appears?" and "how fast does text flow after that?"

5.2 Honest timing on the Mac GPU

PyTorch launches GPU work asynchronously — the Python call returns before the GPU finishes. time.perf_counter() right after model(...) would measure the launch, not the work. The benchmark forces the truth in two ways: it reads the argmax token id (which must wait for the result), and it calls torch.mps.synchronize() before reading the clock.

Watch for

The Task 03 module manual_decode.py times without synchronize. That was fine for teaching shapes on small runs, but it under-reports GPU time. diag_bench.py has its own timed loop for this reason. Same loop shape, honest clocks.

5.3 The measurement protocol

  • Eight prompts, fixed by the brief: two instruction, two JSON extraction, two summarization, two multilingual (Thai and Japanese). They live in configs/benchmark_prompts.json.
  • Prompt lengths near 32, 128, and 512 tokens. The builder repeats a filler sentence into the [FILLER] slot until the templated prompt reaches the target. The real measured count lands in prompt_tokens.
  • One warm-up run, then three measured runs. The first run pays one-time costs: memory allocation and GPU shader compilation. Those costs are real but they are not steady-state speed, so the warm-up run is discarded.
  • 48 generated tokens by default (the brief allows 32–64). Greedy decoding, so the same prompt must give the same tokens every time. Generation may stop early on an end-of-sequence token; then gen_tokens records the real count.
  • Chat template with thinking off. Prompts go through tokenizer.apply_chat_template(..., enable_thinking=False), so the model answers instead of thinking out loud, and JSON checks mean something.

5.4 One JSONL row per measured run

The output file results/09_diag_bench.jsonl is JSONL: one JSON object per line. Important fields:

FieldMeaning
runtimepytorch_local or geniex_qairt_qdc
device, precisionwhere and at what precision the run happened
context_limitthe runtime's context limit: 40960 positions locally, 4096 for the compiled bundle
model_size_bytesparameter bytes locally; the two context-binary files for the bundle
prompt_tokens, gen_tokens, repthe run's real sizes and repetition number
ttft_ms, prefill_tps, decode_tpsthe three metrics from 5.1
peak_rss_bytesthe process's peak resident memory so far, from getrusage. Cumulative over the process, so later rows can only grow. null on the device rows
json_validonly for JSON-extraction prompts: does the output contain one parseable JSON object? null elsewhere
output_failureempty_output, token_loop, or null
output_sha256hash of the generated text. Two runs reproduce when the hashes match. The text itself is not stored
unlike_runtime_warningnull for local rows; a fixed warning sentence on every imported device row
Warning

A missing metric is null, never a guess. The device rows have no json_valid, no peak_rss_bytes, and no output hash, because geniex-bench did not report them. Writing a plausible number there would be fabrication.

5.5 Unlike runtime paths

Your file will hold rows from two worlds: the local float model on this Mac's GPU, and the W4A16 bundle on a Snapdragon NPU. Different hardware, precision, runtime, sampler, and prompt. The import step stamps every device row with unlike_runtime_warning. The rows may sit side by side as context. They must never be averaged or ranked as if they were the same experiment.

6. One worked example

Take the Task 08 device numbers at context 4096: TTFT 19.753 ms with prompt_tokens 128, and decode 108.188 tokens/s.

prefill_tps = 128 tokens / 0.019753 s = 6480 tokens/s
decode step time = 1 / 108.188 tok/s = 9.24 ms per token

Prefill handled a token in about 0.154 ms; decode needed 9.24 ms per token — 60 times more. Same model, same phone, same weights. The only difference is batch shape: 128 tokens per pass vs 1 token per pass. Now suppose someone reported a single number, "(128 + 128 tokens) / (0.020 s + 1.18 s) = 213 tokens/s". That number is real arithmetic and useless: it depends on the prompt/output ratio and describes neither phase. This is why the brief demands the split.

8. Hands-on, in execution order

All commands run from the repo root. No QDC minutes are needed.

  1. Offline tests first: 
    uv run pytest tests/test_task09_bench.py -q
  2. First measured run (about 5–10 minutes; the Mac should be on power, lid open, other heavy apps closed): 
    uv run python -m edge_slm_lab.diag_bench --run-id fp32-a
    Watch the per-prompt lines: prompt_tokens near the targets, TTFT and decode per repetition, and a preview of each output.
  3. Second run, identical settings, for reproducibility: 
    uv run python -m edge_slm_lab.diag_bench --run-id fp32-b
  4. Compare the two runs: 
    uv run python -m edge_slm_lab.diag_bench --check-repro fp32-a fp32-b
    Expect tokens SAME on every line and reproducibility: PASS. Timings may differ a little; token hashes must not.
  5. The parameter change — same benchmark at bfloat16: 
    uv run python -m edge_slm_lab.diag_bench --run-id bf16 --dtype bfloat16
  6. Import your Task 08 device medians as labeled unlike-runtime rows: 
    uv run python -m edge_slm_lab.diag_bench --run-id qdc-774303 \
    --import-geniex /Volumes/T9/qualcomm-edge-slm-lab/artifacts/task08/pulled/results
  7. Look at the finished file: 
    uv run python - <<'EOF'
import json
for line in open("results/09_diag_bench.jsonl"):
    r = json.loads(line)
    print(f"{r['run_id']:<12} {str(r['prompt_id']):<28} rep={r['rep']} "
          f"P={r['prompt_tokens']} ttft={r['ttft_ms']} decode={r['decode_tps']} "
          f"json={r['json_valid']} warn={'yes' if r['unlike_runtime_warning'] else 'no'}")
EOF
Try it

Steps 2–4 ARE the reproducibility experiment, and step 5 is the required parameter change: one variable (precision), two values, same prompts, same machine. Compare decode_tps and check whether the output_sha256 values still match fp32-a.

9. How to read the generated files

  • configs/benchmark_prompts.json — the eight prompts. Each has id, category, language, target_tokens, and for the longer ones a filler sentence and a [FILLER] slot.
  • src/edge_slm_lab/diag_bench.py — read top to bottom: expand_filler (hit the token target), build_prompts (enforce the brief: 8 prompts, 2 per category, Thai present), json_validity and detect_failure (output checks), bench_all (warm-up, reps, row assembly), the timed loop inside run_local (note both sync() calls around each timed region), check_repro, and import_geniex.
  • tests/test_task09_bench.py — the offline tests use a word-count tokenizer and a fake runner, so they check the protocol logic without loading the model.
  • Data flow: prompt text → chat template ids [1, P] → prefill logits [1, P, 151936] → argmax of the last row → decode steps [1, 1] each → one JSONL row per measured run.

10. What to inspect

  • TTFT vs prompt length. Sort the local rows by prompt_tokens. Does ttft_ms grow from the ~32-token prompts to the ~512-token ones? Is the growth roughly linear? Contrast with the device rows, where TTFT was flat because the prompt graph always ran 128 tokens.
  • Decode vs prompt length. Does decode_tps stay roughly flat across prompt lengths? That is the local echo of Task 08's context-length finding.
  • The float-vs-device gap. Local float decode tokens/s vs the device's 108 tok/s — read them side by side, with the warning in mind. This is the deployment gain the project brief asks you to record, not a controlled comparison.
  • json_valid on json_med and json_long: did the model actually produce parseable JSON at both prompt lengths?
  • The Thai and Japanese outputs in the console previews: readable answers in the right language?
  • bf16 vs fp32: decode_tps difference and whether any output_sha256 changed.
  • peak_rss_bytes: read it as "the process needed at most this much memory so far" — it only grows within a run.

11. Common mistakes and debugging clues

  • ERROR: run_id 'fp32-a' already exists — each run appends to the same JSONL, so run ids must be unique. Pick a new id; do not delete the file.
  • First run of everything is slow — that is the warm-up cost the benchmark exists to isolate. Only the warm-up run absorbs it; if rep 1 is still much slower than rep 3, your machine was busy.
  • Decode speeds drift downward across the run — likely thermal throttling. Close other apps, let the Mac cool, rerun with a new --run-id.
  • gen_tokens under 48 with decode_tps present — the model hit end-of-sequence early. Fine: the row records real counts. decode_tps: null happens only when there were zero decode steps.
  • reproducibility: FAIL with differing tokens — check you used the same --dtype and --device in both runs. Greedy decode is deterministic per configuration, not across configurations.
  • Debugging one prompt: add --only json_long to run a single prompt id.
  • Everything in one place looks suspiciously fast — check the sync() calls are still around the timed regions. Without them the clock stops before the GPU finishes.

12. Knowledge check

  1. Why can prefill process 6000+ tokens/s while decode manages about 108 on the same phone?
    AnswerPrefill feeds all prompt tokens in one pass, so the hardware works on many tokens in parallel. Decode feeds one token per pass and must wait for each previous token. The per-pass overhead is paid per 128 tokens in prefill but per single token in decode.
  2. Your file shows local float decode at some tok/s and the device at 108 tok/s. Can you conclude which "is faster"?
    AnswerNo conclusion about the runtimes alone. Hardware, precision, prompt, and sampler all differ — the rows carry unlike_runtime_warning for exactly this reason. You may report both numbers side by side as a deployment observation, never as a controlled comparison.
  3. Why one warm-up run before the three measured runs?
    AnswerThe first run pays one-time costs (memory allocation, GPU shader compilation) that are not part of steady-state speed. Discarding one warm-up run keeps those costs out of the medians.
  4. The benchmark could not read peak memory on the device. What goes in the row?
    Answernull. The brief forbids estimated metrics. A missing measurement stays visibly missing.
  5. Why does the script call torch.mps.synchronize() before reading the clock?
    AnswerGPU work is asynchronous: the Python call returns before the GPU finishes. Without a synchronize, the timer measures the launch time, not the compute time, and the benchmark reports numbers that are too good.

14. Page glossary and sources

JSONL
A text file with one JSON object per line. Easy to append to and to stream through line by line.
Warm-up run
A first, discarded benchmark run that absorbs one-time costs such as memory allocation and shader compilation.
Peak RSS
Peak resident set size: the largest amount of physical memory the process has held so far. Read with getrusage; cumulative over the process lifetime.
Asynchronous execution
The GPU queues work and the CPU call returns early. Honest timing needs a synchronize call so the clock stops only after the work is done.
Unlike runtime paths
Measurements from different hardware, precision, or runtime stacks. They may be shown together with a warning but never averaged or ranked directly.

Official sources: the Qwen3-0.6B model card on Hugging Face (chat template and enable_thinking), the PyTorch MPS backend notes (asynchronous execution and torch.mps.synchronize), and the pinned qualcomm/ai-hub-models tag v0.59.0 for the Task 08 device-side context.
