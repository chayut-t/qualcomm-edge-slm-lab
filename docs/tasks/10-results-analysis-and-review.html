Task 10 — Results analysis and end-to-end review

Lab: one results notebook that reads every earlier record and builds the final report · Estimated time: 1–2 hours · This is the last task.

1. Why this matters for Qualcomm work

Nine tasks produced nine run records and a folder of result files. Each file answered one local question. This task asks the global one: do all those numbers describe one consistent path from Qwen/Qwen3-0.6B on Hugging Face to a quantized program on a Snapdragon NPU?

The check is not an essay. It is code. The notebook loads the real records and runs trace checks — a trace check is a small automated test that a number recorded at one stage matches the number the next stage depends on. Example: Task 02 recorded head_dim = 128 from the Hugging Face config. Task 05 recorded the deployed graph input past_key_0_in with shape [8, 1, 128, 4095]. The 128 in position 2 must be the same 128. If it is, the trace holds at that joint. Eleven such checks cover the whole path.

The core question: how do the outputs from all earlier tasks connect into one model-to-NPU path?

2. What you will understand after this task

These are the twelve concepts the project set out to teach. The final report maps each one to your own recorded evidence.

  1. What happens during prefill and one-token decode.
  2. What is stored in the KV cache, and which dimension grows.
  3. Why GQA uses fewer KV heads than query heads.
  4. Why head_dim can differ from hidden_size / query_heads.
  5. Why an NPU compiler prefers fixed shapes and explicit interfaces.
  6. What crosses the Qualcomm model-part boundary.
  7. What W4A16 means.
  8. What calibration data and quantization encodings are.
  9. What SpinQuant and AdaScale try to improve.
  10. How ONNX, a QNN context binary, QAIRT, and GenieX differ.
  11. Why a bundle is tied to a chipset and compile-time configuration.
  12. Why TTFT and decode tokens/second are separate metrics.

4. A simple mental model

Think of a relay race. The baton is the model. Each task carried it one leg: architecture, decode loop, static graph, adapter, quantization, bundle, device, benchmark. Each runner wrote down what the baton looked like when they held it.

A trace check is the judge comparing two neighboring notes. If runner 2 wrote "8 KV heads of size 128" and runner 5's graph shape also says 8 and 128, the baton was not swapped between them. Eleven passing checks mean one baton crossed the whole course.

Key idea The proof of an end-to-end path is agreement between independent records. Every check compares numbers written by different tasks, on different days, by different code.

5. Exact technical details

5.1 The eleven trace checks

T01HF config (02) hidden_size=1024, 16 query heads, 8 KV heads, head_dim=128; and 128 × 16 = 2048 ≠ 1024, so head_dim is decoupled from hidden_size / query_heads
T02Decode loop (03) KV length grows by exactly 1 per decode step; final_kv_len = prompt_len + generated − 1

6. One worked example: following 128 through the stack

Take the single number head_dim = 128 and watch it survive every stage. All values below come from your own files.

  1. Task 02 — results/02_config_summary.json: "head_dim": 128. Note hidden_size / num_attention_heads = 1024 / 16 = 64, not 128. Qwen sets head_dim independently; the Q projection maps 1024 → 16 × 128 = 2048.
  2. Task 03 — the cache stored 2 × 8 × 128 = 2048 numbers per token per layer (kv_numbers_per_token_per_layer in results/02_parameter_summary.json), and grew by exactly one token per decode step.
  3. Task 05 — the deployed Qualcomm graph declares past_key_0_in: [8, 1, 128, 4095]. Same 8 KV heads, same 128, and 4095 = 4096 − 1 slots because the current token's KV is produced by the graph itself.
  4. Task 08 — the execution manifest records kv_dim = 128 inside the compiled bundle's runtime configuration, and pos_id_dim = 64 — half of 128, because RoPE stores cos and sin for each rotated pair.

One number, four independent records, zero disagreements. That is what "end-to-end" means in this project. T01, T03, and T05 test exactly this thread.

11. Common mistakes and debugging clues

  • FileNotFoundError on a results file — the kernel is running in the wrong directory. The first cell locates the repo root and asserts it; read its error message.
  • A trace check fails after you edited a file — run records and result files are evidence. Never edit them by hand; the checks exist to catch silent drift.
  • The report looks unstyled inside JupyterLab's preview — JupyterLab sandboxes HTML files. Open results/final_report.html in a normal browser tab instead.
  • Reading the deployment plot as "quantization made it 4× faster" — it did not. Different hardware, different precision, different prompt. The gain is real; the attribution is not separable. That is why the warning is on the figure.
  • Stale outputs after changing INCLUDE_BF16 — re-run from the parameters cell down, not just the plot cell; the report cell reads the plot files from disk.

12. Knowledge check

  1. The deployed decode graph input past_key_0_in has shape [8, 1, 128, 4095]. Why 4095 and not 4096?
    AnswerThe context limit is 4096. The graph computes the current token's key and value itself, so the input cache holds at most the 4095 previous positions.
  2. Which two files must agree for trace check T06, and what does their agreement prove?
    AnswerThe Task 07 artifact manifest and the Task 09 device benchmark rows (and the Task 08 manifest) all record 775,835,648 bytes for the context binaries. Agreement proves the phone executed the same compiled artifact the manifest describes — not some other build.
  3. Why does W4A16 make the bundle about 33% of the fp32 size, not exactly 12.5% (4 bits / 32 bits)?
    AnswerOnly weights are 4-bit. The bundle also stores quantization encodings (scales), the embedding, compiled graph structures for every context length, and activation paths kept at 16 bits. Overhead on a 0.6B model is proportionally large.
  4. Local decode speed fell from 31.7 to 22.1 tokens/s as prompts grew, but the phone showed no change between -c 512 and -c 4096. Are these results in conflict?
    AnswerNo. Local runs grew the real KV length (27 → 525 prompt tokens). The phone runs changed only the allocated maximum while the real prompt stayed 128 tokens. Decode cost follows the real cache length, not the configured limit.
  5. GenieX, QAIRT, and the QNN context binary each fix their choices at a different time. Match each to compile time or run time.
    AnswerThe QNN context binary is fixed at compile time (graphs, weights, quantization, chipset). QAIRT's version was fixed when the bundle was compiled against its SDK. GenieX settings — sampler, threads, which compiled context length to load — are chosen at run time, limited by compile-time choices.
