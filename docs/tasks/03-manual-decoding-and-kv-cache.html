Task 03 — Manual decoding and the KV cache

Lab: notebooks/03_manual_decoding_kv_cache.ipynb + src/edge_slm_lab/manual_decode.py + tests/test_manual_decode.py · Estimated time: 2.5–3 hours

1. Why this matters for Qualcomm work

In Task 02 you called model.generate(...). It hid the most important structure in on-device inference: generation is really two different workloads.

  • Prefill — one forward pass over the whole prompt. Input shape [1, P] for a prompt of P tokens.
  • Decode — one forward pass per new token. Input shape [1, 1], plus the stored KV cache of everything before.

Qualcomm's compiled bundle contains separate graphs for these two workloads, each with fixed shapes. Benchmarks report them separately: time-to-first-token measures prefill, tokens per second measures decode. When Task 04 asks "why does the NPU need two graph contracts?", the loop you build today is the answer.

4. A simple mental model

Generation is autoregressive: each new token is chosen from the model's output, then appended to the input for the next round. The naive way to do that reruns the whole growing text every round — wasted work, because tokens never change once written.

Attention needs three things per token: a query Q, a key K, and a value V. Here is the trick. K and V for token 12 depend only on tokens 1–12, which never change. So compute them once, store them, and reuse them forever. That store is the KV cache.

With the cache, each decode round only needs the newest token: compute its Q, K, V; append K and V to the cache; let the new Q attend over every stored K and V. One token in, one token out, cache one longer.

Key idea The KV cache trades memory for compute. Per layer, Qwen3-0.6B stores 2 × 8 × 128 = 2,048 numbers per token (K and V, 8 heads, head dim 128). Across 28 layers that is 57,344 numbers per token. This is the memory that grows during generation, and it is why the compiled NPU bundle must fix a maximum context length ahead of time.

5. Exact technical details

Shapes for batch 1, prompt length P, T = tokens seen so far:

TensorPrefillOne decode step
input_ids[1, P][1, 1]
logits[1, P, 151936][1, 1, 151936]
cache K per layer[1, 8, P, 128][1, 8, T, 128]
cache V per layer[1, 8, P, 128][1, 8, T, 128]
attention scores[1, 16, P, P][1, 16, 1, T]

Three details that matter:

  • Which logits row picks the next token. After prefill, logits have one row per prompt token. Only the last row — logits[0, -1] — scores the next token. The other rows are by-products of computing the cache.
  • The cache API. model(...) with use_cache=True returns out.past_key_values, a DynamicCache object. In transformers 4.57.6 the tensors live at cache.layers[i].keys and .values. Older versions used cache.key_cache. The module's get_kv() helper handles both.
  • The off-by-one. The last generated token is chosen but never fed back, so its K/V are never computed. Final cache length is P + generated − 1, not P + generated. The notebook asserts this exact formula.
Watch for Attention scores in a decode step are [1, 16, 1, T] — one query row against T keys. That is a thin matrix–vector-like workload, usually memory-bound. Prefill's [1, 16, P, P] is a fat matrix–matrix workload, usually compute-bound. Same weights, different hardware behavior. This is why the two metrics in Task 09 (TTFT and tokens/s) must never be merged into one number.

6. One worked example — the loop, line by line

This is the core of src/edge_slm_lab/manual_decode.py, the code you will run. Read it with the comments here.

out = model(input_ids=input_ids, use_cache=True)

Prefill. The whole prompt [1, P] goes through all 28 blocks once. use_cache=True asks the model to keep every layer's K and V.

cache = out.past_key_values
next_id = int(out.logits[0, -1].argmax())

Keep the filled cache. Then greedy choice: logits[0, -1] is the score row of the last prompt token — 151,936 numbers — and argmax() picks the id with the highest score.

for step in range(1, max_new_tokens):
    step_input = torch.tensor([[next_id]], device=input_ids.device)

The decode loop. The input is only the newest token, shape [1, 1]. History travels through the cache instead.

    out = model(input_ids=step_input, past_key_values=cache, use_cache=True)
    cache = out.past_key_values

One forward pass. past_key_values=cache hands the model its memory. The model computes K/V for one new token, appends them, and returns the grown cache. The position of the new token is inferred from the cache length.

    next_id = int(out.logits[0, -1].argmax())
    trace.steps.append({... "kv_len": kv_shape(cache)[2] ...})

Greedy choice again, and one trace entry per step. kv_shape(cache)[2] reads the third axis of the layer-0 key tensor — the axis that grows. The loop also stops early if next_id equals eos_token_id, the model's end-of-message marker.

12. Knowledge check (optional)

1. Prefill input is [1, 24]. What shape are the logits, and which row picks the next token?

Logits are [1, 24, 151936] — one score row per prompt token. Only the last row, logits[0, -1], picks the next token. The other 23 rows are by-products.

2. What exactly does the cache store per layer, and which axis grows?

The key and value tensors for all past tokens: K and V each [1, 8, T, 128]. The third axis T — one slot per token seen — grows by 1 per decode step.

3. Why can a decode step feed only [1, 1] without losing the history?

Attention reads the history through the cached K and V. The new token's query attends over all stored keys and values, so nothing from the past needs to be recomputed or re-fed.

4. After a 24-token prompt and 16 generated tokens, why is the cache length 39 and not 40?

The 16th token is chosen from logits but never fed back, so its K/V are never computed. 24 + 16 − 1 = 39.

5. Why does one decode step cost much less time than prefill, even though both run all 28 blocks?

Prefill processes all 24 tokens at once — every matrix multiply is 24 rows deep. A decode step processes 1 row. The weights read are the same, but the arithmetic is about 24× smaller. On an NPU this is also why decode is memory-bound: moving weights dominates.

14. Page glossary and sources

New terms, also in the project glossary:

  • Autoregressive — generating one token at a time, feeding each output back as input.
  • Prefill — the single forward pass over the whole prompt that fills the KV cache.
  • Decode — the repeated one-token forward pass that extends the KV cache.
  • EOS token — the special id that marks the end of a message; generation stops there.
