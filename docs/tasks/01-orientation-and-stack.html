Task 01 — Orientation, access, and stack map

Lab: notebooks/01_environment_and_access.ipynb · Estimated time: 2.5–3 hours

1. Why this matters for Qualcomm work

Every later task depends on two things: a working local environment and access to Qualcomm's tools. If either is broken, you find out today, not in week two.

The Qualcomm stack has many names: AIMET, AI Hub, QNN, QAIRT, GenieX, QDC. People mix them up. This task gives each name one job in your head. That map makes every later error message readable.

2. What you will understand after this task

  • What each layer of the Qualcomm deployment stack does.
  • Which Qualcomm devices, chipsets, and runtimes you can reach today.
  • Which deployment route this project will try first, and the fallback.
  • Where credentials live in this repository and why they never appear in outputs.

3. Prerequisites

None. This is the first task. You need the Python environment from the project README:

uv venv --python 3.11

4. A simple mental model

Think of shipping a meal, not code:

  • Hugging Face model — the recipe. Flexible, runs anywhere, slow on small hardware.
  • AIMET — the nutritionist. It shrinks the recipe (quantization) with little quality loss.
  • AI Hub Workbench — the factory kitchen. It compiles, checks, profiles, and packages the model for one exact device family.
  • QNN context binary — the frozen ready-meal. Compiled for one chipset. It cannot change shape after packaging.
  • QAIRT — the microwave. The runtime on the device that executes the compiled graph.
  • GenieX — the waiter. The interface you talk to. It feeds prompts in and streams tokens out through a backend.
  • QDC — the tasting room. Remote access to real Snapdragon devices.
Key idea A compiled bundle is frozen at compile time: precision, graph shapes, KV-cache layout, context limit, and chipset. These are not runtime settings. This one fact explains most compatibility errors you will see.

Two PyPI packages share a similar name. Keep them apart:

  • qai-hub-models-cli==0.59.0 — light discovery CLI. Already in requirements-core.txt.
  • qai-hub-models==0.59.0 — heavy model package. Installed later, only when a task needs it.
Watch for Do not assume every bundle exists for every QDC device. This task's job is to discover today's real combination. The route order is:
  1. Qwen3-0.6B W4A16 QAIRT bundle on a compatible QDC device through GenieX.
  2. Qwen3-0.6B W4A16 compiled, profiled, and inferred on a hosted AI Hub physical device.
  3. GGUF through GenieX on QDC, plus a separate QAIRT profile through AI Hub. These are different runtime paths.

6. One worked example

Here is what one discovery command looks like and how to read it. Your exact output will differ — that is the point of discovery.

$ qai-hub-models devices
Name                          OS         Chipset
Samsung Galaxy S24 (Family)   Android 14 qualcomm-snapdragon-8gen3
Snapdragon X Elite CRD        Windows 11 qualcomm-snapdragon-x-elite
...

Read each row as: a physical device family, its OS, and the chipset a context binary would be compiled for. The chipset column is the one that matters for bundle compatibility.

  1. Make sure the environment exists: 
    uv venv --python 3.11
uv pip install -r requirements-core.txt
  2. Start JupyterLab from the project root:

  3. Open notebooks/01_environment_and_access.ipynb.
  4. Run the cells top to bottom. Read the note above each cell first.

9. How to read the notebook

The notebook has four parts, in order:

  1. Setup and secrets — loads paths and checks the token file without printing it.
  2. Local inventory — records OS, architecture, Python, disk, and key package versions to results/01_environment_inventory.json.
  3. Access checks — Hugging Face and Qualcomm AI Hub. Each check reports ok, missing, or an error summary. No model download happens.
  4. Qualcomm discovery — runs the CLI with --help first, then real discovery commands such as qai-hub-models devices, chipsets, runtimes, and info Qwen3-0.6B. Sanitized output goes to results/01_qualcomm_discovery.json.

12. Knowledge check

Optional. Answers are hidden until you click.

1. Which artifact is tied to one specific chipset?

The QNN context binary. It is compiled ahead of time for one target platform. The Hugging Face model and GGUF files are portable.

2. What is the difference between QAIRT and GenieX?

QAIRT is the runtime suite that executes compiled graphs on the device. GenieX is the interface layer above it that manages generative-AI execution through a backend such as qairt or llama.cpp.

3. Which layer freezes the maximum context length?

AI Hub compilation. Context limit, graph shapes, KV-cache layout, and precision are fixed when the context binary is built. GenieX cannot change them at runtime.

4. Why does this project install two different Qualcomm packages?

qai-hub-models-cli is a light CLI for discovery. qai-hub-models is the heavy model package with export dependencies. Keeping them separate keeps the core environment small and stable.

5. GenieX can run Qwen3-0.6B through qairt or through llama.cpp. Are results from the two comparable as the same runtime?

No. The qairt path runs a chipset-specific QNN context binary on the NPU. The llama.cpp path runs a GGUF model, a different format on a different execution path. Always label them as different runtime paths.
