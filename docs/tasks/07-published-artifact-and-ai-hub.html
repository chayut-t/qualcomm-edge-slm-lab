5. Exact technical details

5.1 The published artifact

Qualcomm releases pre-built assets per model, per release tag. Your Task 01 discovery already found the only Qwen3-0.6B asset in release v0.59.0:

PrecisionRuntimeChipsetsSDK
w4a16GenieX (QAIRT) Dragonwing IQ-9075, SA8775P, Snapdragon 8 Elite Gen 5 Mobile, Snapdragon 8 Elite Mobile, Snapdragon X Elite, Snapdragon X2 Elite QAIRT 2.45.0.260326154327

Facts to notice. There is no float, no w8a8, no other precision — W4A16 is the only choice, matching SUPPORTED_PRECISIONS from Task 06. The runtime is geniex_qairt: the GenieX LLM runtime on top of QAIRT (Qualcomm AI Runtime). And you must pick a chipset, because the compiled program inside is chipset-specific.

5.2 Chipset, not device

A QNN context binary is compiled ahead-of-time for one NPU generation. The chipset ID names that target:

  • qualcomm-snapdragon-8-elite = sm8750 — Snapdragon 8 Elite Mobile. Reference phones like the "Snapdragon 8 Elite QRD".
  • qualcomm-snapdragon-8-elite-for-galaxy = sm8750-ac — the same chip, higher clocks, used in the Samsung Galaxy S25 family. Same NPU architecture (HTP version 79).

Your recorded route targets a Galaxy S25 on QDC (Task 08). The bundle is published for qualcomm-snapdragon-8-elite. Because both variants share HTP version 79, one binary serves both — this is exactly the kind of claim your device job can test. Label: the shared-HTP fact comes from Task 01's device table; the "one binary serves both" part is an inference you will check.

5.3 AI Hub job types

AI Hub runs jobs on hosted physical devices. Four kinds matter:

JobInputOutputYou use it when
Compilesource model (ONNX, TorchScript) compiled model (context binary, DLC, TFLite) you bring your own model
Linkseveral compiled graphs one context binary with shared weights prefill + decode graphs must share weights
Profilecompiled model timing, memory, per-layer placement you want performance numbers
Inferencecompiled model + input tensors output tensors you want to check numerical outputs

You will run a profile job. It answers this task's question directly: it loads your fetched binary onto a real Snapdragon NPU and measures what happens.

5.4 What a profile job reports

The key fields, all times in microseconds (µs):

  • first_load_time — first load on the device. Includes preparing the context on the NPU. Usually the biggest number.
  • warm_load_time — loading again after the device has cached the prepared context. This is what an app user feels on second launch.
  • estimated_inference_time — one forward pass of the compiled graph. For an LLM part this is one graph invocation, not one full generated sentence.
  • inference_memory_peak_range — bytes of peak memory during inference, as a [low, high] range.
  • Per-layer compute unit placement — NPU, GPU, or CPU for every layer. For this bundle you expect NPU everywhere.

5.5 Fetch versus export

qai-hub-models fetch downloads the finished shelf product. qai-hub-models export would rebuild it from source through AI Hub Workbench: quantize (hours, GPU), convert, compile per chipset, link. The export path needs the heavy qai-hub-models package from requirements-qualcomm.txt and a lot of compute. This task uses fetch. Export stays a concept — you already studied its quantize phase in Task 06.

5.6 The two CLIs and the two scripts

Two different command-line tools, easy to confuse:

  • qai-hub-models — the model catalog CLI. Knows about published assets. You used it in Task 01.
  • qai-hub — the AI Hub client CLI. Talks to your account: devices, uploads, jobs. Newly installed for this task (qai-hub==0.55.0, recorded in progress/decision_log.md).

Two new small scripts in src/edge_slm_lab/:

  • artifact_manifest.py — walks the fetched bundle and writes results/07_artifact_manifest.json: per file the relative path, size, sha256 hash, and a guessed kind. It refuses to write anything containing a URL or token-like string (sanitize.py holds the shared check).
  • hub_job_record.py — takes a job ID, waits for the job, and writes a sanitized record into results/07_hub_job.json. It copies only a fixed list of fields, so nothing from the raw profile can leak. Missing metrics stay null; nothing is estimated. Records merge by job ID, so several jobs share one file.

5.7 Inside a context binary: many graphs

A context binary is not one program. Your fetched parts each hold ten graphs: a prompt (prefill, AR-128) and a token (decode, AR-1) graph, each compiled at five context lengths:

prompt_ar128_cl512_1_of_2    token_ar1_cl512_1_of_2
prompt_ar128_cl1024_1_of_2   token_ar1_cl1024_1_of_2
prompt_ar128_cl2048_1_of_2   token_ar1_cl2048_1_of_2
prompt_ar128_cl3072_1_of_2   token_ar1_cl3072_1_of_2
prompt_ar128_cl4096_1_of_2   token_ar1_cl4096_1_of_2

Part 2 has the same ten with the _2_of_2 suffix. The name pattern comes from the pinned source (_shared/llm/model.py, _build_graph_names): {prompt|token}_ar{seq_len}_cl{ctx_len}_{part}_of_{splits}.

This is Task 04 pushed to its conclusion. A static graph fixes both the input length (AR) and the attention span (CL). One graph per combination. Fact: the graphs exist — you can list them yourself (step 6 below). Inference: Genie switches among the context lengths as a conversation grows, so short chats do not pay for a 4096-token attention span.

Profiling consequence: a profile job on a multi-graph binary must name one graph, or the device refuses to load it with:

Error loading: Models with multiple graphs must specify a graph name to use. Use --qnn_options context_enable_graphs=<graph name>.

6. One worked example: reading a profile record

The numbers below are illustrative, invented for teaching. Your real numbers replace them. Suppose results/07_hub_job.json shows:

"metrics": {
  "estimated_inference_time_us": 38000,
  "first_load_time_us": 2100000,
  "warm_load_time_us": 260000,
  "estimated_inference_peak_memory_bytes": 410000000,
  "inference_memory_peak_range_bytes": [380000000, 410000000],
  "layers_per_compute_unit": {"NPU": 812}
}

How to read it: one graph pass takes 38 ms. First load costs 2.1 s but a warm load only 0.26 s — the device caches the prepared context. Peak memory is about 410 MB, which fits the Task 06 size estimate (~284 MiB of 4-bit weights plus activations and runtime overhead). Every one of the 812 layers ran on the NPU; a single CPU layer here would be a red flag for a fallback.

8. Hands-on instructions

Run everything from the repo root. Every command starts with uv run — plain qai-hub-models is not on your PATH.

  1. Check the drive and make the target folder: 
    df -h /Volumes/T9
mkdir -p /Volumes/T9/qualcomm-edge-slm-lab/artifacts/task07
  2. Fetch the published bundle (large download; goes to T9, never the repo): 
    uv run qai-hub-models fetch Qwen3-0.6B \
  -r geniex_qairt -p w4a16 -c qualcomm-snapdragon-8-elite \
  -o /Volumes/T9/qualcomm-edge-slm-lab/artifacts/task07
  3. Build the sanitized manifest (point it at the extracted bundle folder that step 2 printed): 
    uv run python -m edge_slm_lab.artifact_manifest \
  /Volumes/T9/qualcomm-edge-slm-lab/artifacts/task07 \
  -o results/07_artifact_manifest.json
  4. Run the offline tests for both scripts: 
    uv run pytest tests/test_task07_tools.py -q
  5. Confirm the hosted device exists right now (never trust a pasted device name): 
    uv run qai-hub list-devices 2>&1 | grep -i "8 Elite"
  6. List the graph names inside the binary you will profile (graph names are stored as plain strings in the file): 
    grep -aoE "(prompt|token)_ar[0-9]+_cl[0-9]+_[0-9]_of_[0-9]" \
  <path-to-one-context-binary> | sort -u
    Expect ten names per part (section 5.7).
  7. Submit one profile job. Pick the smallest context binary from the manifest first — it uploads faster — and name one graph. Use the token (decode) graph at full context; it is the graph that runs most during generation: 
    uv run qai-hub submit-profile-job \
  --model <path-to-one-context-binary-from-the-manifest> \
  --device "Snapdragon 8 Elite QRD" \
  --name "qwen3-0.6b w4a16 task07 part1 token graph" \
  --profile_options "--qnn_options context_enable_graphs=token_ar1_cl4096_1_of_2"
    For part 2 the graph suffix changes to _2_of_2. The command prints a job ID (like jp8m66x2g) and a dashboard link. The job queues, uploads, runs, and can take many minutes.
  8. Record the job (this waits until the job finishes): 
    uv run python -m edge_slm_lab.hub_job_record <JOB_ID> \
  -o results/07_hub_job.json
  9. Comparison experiment (required): submit one more profile job, changing exactly one thing — a different context-binary part (same device, same graph role), a different graph in the same part (prompt_ar128_cl4096_... vs token_ar1_cl4096_...), or --device "Samsung Galaxy S25 (Family)" (same binary, the sm8750-ac variant). Record it with the same command; the record file merges by job ID.
Watch for

A failed job is still evidence — record it with hub_job_record and read its runtime log on the dashboard. The known failure: submitting a part without --profile_options fails with the multi-graph error quoted in section 5.7. The fix is naming a graph, not a different model. If the device still rejects the binary for another reason, do not burn hours. Record the failure, then run the documented fallback: compile and profile the small Task 04 graph on the same device:

uv run qai-hub submit-compile-and-profile-jobs \
  --model artifacts/onnx/tiny_prefill_p16.onnx \
  --device "Snapdragon 8 Elite QRD" \
  --compile_options "--target_runtime qnn_context_binary"

Record both resulting job IDs. That still gives you a hosted-device compile and profile record for this task's gate.

9. How to read the generated files

  • src/edge_slm_lab/sanitize.py — 25 lines. One list of forbidden substrings, one function. Both scripts call it before writing. Read it first; it is the safety contract.
  • src/edge_slm_lab/artifact_manifest.py — data flow: rglob every file → classify by name → hash and size → totals by kind → refuse-or-write. classify() is a heuristic; the field is honestly named kind_guess.
  • src/edge_slm_lab/hub_job_record.py — data flow: job ID → qai_hub.get_job → job.wait() → for a successful profile job, job.download_profile() → extract_metrics() copies a fixed whitelist (METRIC_KEYS) and counts layers per compute unit → merge into the output keyed by job ID. Note what it never does: it never dumps the raw job object, and never fills a missing metric.
  • tests/test_task07_tools.py — offline tests with a fake bundle and fake profile dicts. Shows the expected shapes of both output files.

10. Outputs to inspect

  • In results/07_artifact_manifest.json: how many qnn_context_binary files, and their total bytes. Compare against the Task 06 estimate of ~284 MiB for the weights alone. Find the genie_config and tokenizer entries — the bundle carries the whole runtime contract, not just weights.
  • In the fetch output: the extracted folder name and the QAIRT SDK version it was built with.
  • On the job dashboard (the link the submit command printed): the timeline — queued, uploading, running — and the per-layer view.
  • In results/07_hub_job.json: status.code, then first_load_time_us vs warm_load_time_us (expect a big gap), estimated_inference_time_us, and layers_per_compute_unit (expect NPU only). Compare the two recorded jobs: what did your one changed variable change? For a part1-vs-part2 pair, expect part2 (the 28 transformer layers) to be much slower than part1 (the embedding lookup).

11. Common mistakes and debugging clues

  • zsh: command not found: qai-hub-models — the tools live in the project venv. Prefix every command with uv run.
  • Fetch fails with a filter error — copy the exact flags from step 2. Values come from fetch --help; older releases used different runtime names.
  • Download lands in the repo — you forgot -o. Delete it from the repo, refetch to T9. Never commit it.
  • Job fails with Error loading: Models with multiple graphs must specify a graph name to use. Use --qnn_options context_enable_graphs=<graph name>. — you submitted a part without naming a graph. Add --profile_options "--qnn_options context_enable_graphs=<name>" with a name from step 6, and make sure its _1_of_2 / _2_of_2 suffix matches the part.
  • Requested device not available — device names drift. Rerun step 5 and copy the name exactly, including "(Family)" if you use the Galaxy alias.
  • The job sits in "queued" — hosted devices are shared. Minutes is normal. The record script's wait() handles it; leave it running.
  • hub_job_record prints REFUSED to write — the sanitizer found a URL-like string. That is the tool doing its job; tell Claude what it found instead of bypassing it.

12. Knowledge check

  1. Why does the fetch command need a chipset flag?
    AnswerThe bundle contains QNN context binaries, which are compiled ahead-of-time for one NPU generation. A different chipset needs a different compiled asset.
  2. What is the difference between qai-hub-models and qai-hub?
    Answerqai-hub-models is the model catalog CLI (published assets, per-model info). qai-hub is the AI Hub client (your account: devices, uploads, jobs).
  3. A profile record shows first_load_time_us: 2100000 and warm_load_time_us: 260000. Why the gap?
    AnswerFirst load prepares the context on the NPU; the device caches that prepared state, so later loads skip the expensive preparation.
  4. Why does hub_job_record.py copy a fixed whitelist of fields instead of saving the whole profile?
    AnswerThe raw job data can contain signed download URLs. Copying only known metric keys makes leaking a secret into the committed record impossible.
  5. Your job reports 3 layers on CPU and the rest on NPU. Good or bad?
    AnswerBad sign — a fallback. Those layers were not compiled for the NPU and will be slow and power-hungry. For this fully quantized published bundle you expect everything on the NPU.

14. Page glossary and sources

AI Hub job
One unit of work on Qualcomm AI Hub: compile, link, profile, or inference. Each job gets an ID and runs on a chosen hosted device.
Hosted device
A physical phone or board in Qualcomm's lab that AI Hub jobs run on. Shared, queued, and free to use with an account.
Profile job
An AI Hub job that loads a compiled model on a hosted device and measures load time, inference time, memory, and per-layer compute-unit placement.
Bundle (GenieX QAIRT)
The published package for an LLM: QNN context binaries plus the runtime configs and tokenizer that GenieX needs to run them.
